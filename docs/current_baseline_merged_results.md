# 当前已完成基线：两种合并训练方案的结果审计

用户上传 `current_baseline_results.tar.gz`，共60个文件。包含两套方案×3数据集的6组开发、6组最终合并重训，以及预训练来源记录、4份下游预算JSON和1K子集清单。包内另有两个存在冲突的旧1080行1K开发结果，不纳入本报告成绩表。

SR=SROCC、PL=PLCC，顺序严格按CSV原字段。所有refit指标是固定预算结束点的单次最终测试，不按测试选择轮次。

## 两种方案和真实模型版本

- **both / 仅下游合并**：预训练原划分验证component-anchor选第5轮来源；两个阶段均无质量文本CE/负例push。下游重新开发定预算，再train+val合并。
- **allmerged / 两阶段合并**：预训练先独立开发选第9轮预算，再从初始编码器合并RichHF train+val；其结束点表示初始化三个下游。下游也重新开发、train+val合并。

**按包内配置和记录提交，这批仍对应I-I输入g的历史版本，而不是后来新增的`image_image_feature: z`版本。** 两个预训练配置都没有z选项；包内没有zii实验记录。不能把本报告分数作为最终z-I-I框图的实验结果。所有下游global Q/A输入g与原设置一致。

预训练来源SHA256：

- both: `a007251cfd4e54ea17c2c270eaaf0f22ebefcb77834e144caf09c9e43f2126a5`
- allmerged: `85d89ac3611c5872e0d6785b7ee7d18ebe1a8d3073b3da9e413d6eb7d31287eb`

每个方案的三数据集和dev/refit来源记录一致，checkpoint_verified_after_load=true。包中不含权重，未独立重算pth摘要。

## 后续建议

本轮先把两套完整结果固定归档，不再按测试结果追加调参或挑中间轮。若继续落实用户已指定的I-I z输入，应建立新的预训练来源并重新确定下游预算；不能把这里g版本的权重改名当成z版本。若研究合并机制本身，则应从同一个开发实验及其固定预算派生两条训练路线，另做受控比较。
